## §2  Case A–D judgment rules

### Case A — login_failed (transport failure)

**Trigger:** `live_broker_login_failed` in log, `error_code=login_failed`

**Evidence to record in SSOT §3.1:**
```
[OBSERVED] trading-day after-hours Shioaji login: FAILED (transport)
[OBSERVED] order_journal: INTENT -> FAILED.transport
[INFERRED] after-hours contract fetch: not reached
[ASSUMED]  production after-hours login behavior may differ from sim
```

**Merge decision:** DO NOT merge to main.
- Rationale: P-obs-1 core observation incomplete; after-hours
  login behavior still `[ASSUMED]` for trading-day scenario.
- Action: keep branch open, record in §3.1, wait for next
  observation window.

**Invariant check:**
- positions table must have NO new rows (Q5)
- orders table status = FAILED, filled_shares = 0

---

### Case B — login ok, place_order rejected (broker_reject)

**Trigger:** login succeeds, then `order_failed` with
`failure_type=broker_reject` or similar non-transport error code

**Evidence to record in SSOT §3.1:**
```
[OBSERVED] trading-day after-hours Shioaji login: SUCCESS
[OBSERVED] after-hours place_order: REJECTED by broker
[OBSERVED] reject type: <error_code from log>
[OBSERVED] shioaji_raw_submit_observation: fired (high value)
```

**Merge decision:** CONDITIONAL — only if rejection semantics are
explicit and expected.

Merge ALLOWED if error_code is one of:
  - `market_closed` / `after_hours_not_allowed` (or semantic equivalent)
  - Any rejection that is broker-documented, expected for after-hours,
    and carries no ambiguity about what was attempted

Merge NOT ALLOWED if error_code is any of:
  - `unknown_error` or unrecognized error code
  - `malformed_order` / `invalid_contract` / `invalid_price`
  - Any error class not previously observed in sim
  Rationale: an unknown rejection class means we do not know what
  the broker rejected or why. Merging code that produced an unknown
  error is merging unverified behavior.

If merge is allowed:
  - Live unlock: still NO (G1–G6 not satisfied)
  - Action: fill §3.1 checklist fully, update §5 resolved invariants
    if `shioaji_raw_submit_observation` captured trade_type / status_type

**Invariant check:**
- positions table must have NO new rows (Q5)
- orders table status = FAILED, filled_shares = 0
- `shioaji_raw_submit_observation` in audit output → record
  trade_type, status_type, status_status_repr

### Case C — login ok, order SUBMITTED, no fill (after-hours acceptance)

**Trigger:** `order_intent_recorded` + broker_order_id present,
status = SUBMITTED, filled_shares = 0

**Evidence to record in SSOT §3.1:**
```
[OBSERVED] trading-day after-hours Shioaji login: SUCCESS
[OBSERVED] after-hours place_order: ACCEPTED (SUBMITTED)
[OBSERVED] broker_order_id: <value>
[ASSUMED]  whether this order will fill at T+1 open or expire
[ASSUMED]  broker after-hours order handling semantics
```

**Merge decision:** DO NOT merge until reconcile outcome known.
- A SUBMITTED order with no fill confirmation is a non-terminal
  state. Merging while an unresolved order exists creates an audit
  gap if anything goes wrong overnight.
- Action: wait for T+1 startup_recovery to resolve SUBMITTED,
  then re-evaluate merge.
- CRITICAL: monitor T+1 08:30 — does order fill at open?
  If yes, this becomes the first end-to-end P-obs-2 candidate.

**Overnight risk — DO NOT modify schema or execution code while
unresolved SUBMITTED exists.**
An overnight queued order may execute before the next observation
window. If execution code or startup_recovery semantics are changed
while the order is still live at the broker, the recovery path may
behave differently from what the new code expects. Freeze all
execution changes until the SUBMITTED order reaches a terminal state
(FILLED / FAILED / EXPIRED) and is confirmed in both orders journal
and positions table.

**Invariant check:**
- positions table must have NO new rows (Q5) — SUBMITTED ≠ FILLED
- orders table status = SUBMITTED, filled_shares = 0
- broker_order_id is not null

## §4  Rollback gate

Rollback to pre-P-obs-1 state (3cc7c0a) if ANY of these fire:

**Hard rollback triggers:**
- [ ] daily_run crashes before shutdown_guard summary line
- [ ] Schema / migration error appears in logs
- [ ] orders row missing fill_date OR requested_lots OR filled_shares
      (NULL where a value is required)
- [ ] FAILED or SUBMITTED order causes a new row in positions table
      (INV-4 violation — only FILLED opens position)
- [ ] `result.success` path appears in execution logs
      (forbidden pattern per execution_model.md §10)
- [ ] cron chain resumes execution after daily_run failure
      without HELIOS_SKIP_EXIT_SCAN=1 present

**Soft rollback triggers (investigate before deciding):**
- [ ] audit script shows parse failures on ALL observation lines
      (suggests structlog JSONRenderer serialization broke)
- [ ] `shioaji_raw_submit_observation` missing despite order being placed
      (suggests P-obs-1 patch not active or log level filtered)
- [ ] deals_paths_agree = False in audit output
      (SDK path divergence — high-value anomaly, record in §4 before rollback)

**BEFORE DB/code rollback — broker-side cleanup (Case C only):**

If the observed case is C (SUBMITTED overnight), verify no live
broker-side order remains queued before executing any rollback:

```bash
# Check for active broker order

    SELECT order_id, symbol, broker_order_id, status, submitted_at
```

If broker_order_id is present and status = SUBMITTED:
  Option A (preferred): cancel the order at broker via Shioaji app
    or API before rollback. Confirm cancellation, then proceed.
  Option B (if cancel not possible): record broker_order_id in
    rollback notes. After rollback, monitor broker account manually
    until order is confirmed expired or cancelled.

**WARNING:** Rolling back locally while a live broker order exists
creates broker truth != internal truth. This is exactly the
position desync described in execution_model.md §14 Risk 5.
Do not proceed with rollback until broker-side state is confirmed
clean or explicitly documented.

written during the observation window may reference order_ids or
states that differ from pre-patch expectations. If in doubt, restore
the DB snapshot first.
