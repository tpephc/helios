## Design Summary

State machine zones per position:
trailing_stop  = max_close_since_entry - 2.0 × entry_atr
approach_enter = trailing_stop + 0.5 × entry_atr
approach_exit  = trailing_stop + 0.8 × entry_atr
NORMAL → APPROACH: price ≤ approach_enter
APPROACH → NORMAL: price > approach_exit  (dead-band: 0.3×ATR)

→ BREACH:        price ≤ trailing_stop  (unconditional)
BREACH → APPROACH: trailing_stop < price ≤ approach_exit
BREACH → NORMAL:   price > approach_exit
Key guarantees:
- Notify only — positions table never written
- Outbox: DB COMMIT before Telegram send
- Idempotency: UPDATE...RETURNING (not SELECT-after-UPDATE)
- System alert isolation: bot failure does not interrupt position supervision
- System alert cooldown: 60 min

## Addendum 1 — Operator-scoped execution isolation (2026-05-22, revised)

### Core principle
Operator identity, risk limits, approvals, and broker routing
must be isolated at the execution layer and never coupled to
signal generation semantics.
### Architecture constraints

**1. operator_id is the execution-domain primary key**

Telegram is transport layer, not execution identity.
operator_id (internal UUID)
↓
telegram_chat_id
↓
telegram transport
Future transports (web UI, Discord, REST API) must not require schema changes.

**2. broker_accounts is separate from operators**

One operator → multiple accounts (personal, corporate, paper, test).
Credential rotation must not touch the operator row.

**3. signals bind to operator_id, not chat_id**

Transport identity must not enter core execution schema.
incoming_chat_id → resolve operator_id → verify signal.operator_id == sender.operator_id
**4. position.operator_id is immutable**

Reassigning a position to another operator corrupts PnL attribution,
risk aggregation, execution audit, and compliance trace.
This must be a DB-level and application-level invariant.

**5. Signal generation must not know operator routing**
strategy
↓
candidate signals (market facts)
↓
allocation / operator routing
↓
approval
↓
execution
Signal engine produces `AAPL breakout`, not `send to Philip`.

## Addendum 2 — Multi-operator architecture review (Advisor K, 2026-05-22)

### P0 decisions needed before v0.1.16 implementation

**1. Authorization identity: telegram_user_id, not chat_id**

`chat_id` identifies a conversation, not a person.
`from_user.id` (Telegram user_id) is the correct identity for approval authorization.
`chat_id` is for sending notifications; `user_id` is for verifying who approved.
operators.telegram_user_id  ← from update.message.from_user.id
operators.telegram_chat_id  ← for sending notifications (separate concern)
**2. Signal scope: per-operator signal (Option A)**

A global signal cannot account for per-operator capital_limit, allowed_symbols,
and entry parameters. Each operator runs strategy evaluation independently.
strategy.evaluate(operator_id=X) → signal for operator X
strategy.evaluate(operator_id=Y) → signal for operator Y
Signal generation must not know operator routing; the allocation layer
calls strategy evaluation once per operator.

**3. committed_notional = approved_pending + open_positions**

`capital_limit` check at approve time must be atomic:

```sql
-- inside approve transaction
SELECT capital_limit, committed_notional FROM operators WHERE operator_id = ?
-- if requested_notional + committed_notional > capital_limit → REJECT
UPDATE operators SET committed_notional = committed_notional + ? WHERE operator_id = ?
```

Decrement `committed_notional` on position close and on signal expiry/rejection.

**4. Shioaji multi-account login: verify before designing**

Shioaji SDK may not support multiple simultaneous logins in one process.
Verify before deciding on client lifecycle strategy (persistent vs lazy vs pool).

### P1 — do now (pre-Shioaji)

Add `operator_id` to existing tables with a default value.
Zero migration cost; enables future routing without schema changes.

```sql
ALTER TABLE signals   ADD COLUMN operator_id TEXT DEFAULT 'default';
ALTER TABLE positions ADD COLUMN operator_id TEXT DEFAULT 'default';
```

`position.operator_id` must be treated as immutable after insert.
Add to invariant tests when implementing.

### P2 — with Shioaji (v0.1.16)

Replace `allowed_symbols TEXT` (JSON) with junction table:

```sql
CREATE TABLE operator_symbols (
    operator_id TEXT NOT NULL,
    symbol      TEXT NOT NULL,
    PRIMARY KEY (operator_id, symbol)
);
```

Full `operators`, `broker_accounts`, `risk_profiles`, `approval_requests`
schema per Addendum 1.

## Addendum 5 — Regime exit design review (Advisor C, 2026-05-22)

### Current design
regime != 'bull' → full exit (binary kill switch)
Based on TAIEX SMA200 + vol_20 threshold (2%).

### What works
- Statistical basis: Taiwan market is highly index-driven
- Cross-sectional correlation spikes in stress regimes
- Conservative approach is appropriate for v0.1 paper trading

### Primary risk: regime flip noise
In sideways/choppy markets, SMA200 crossings generate false transitions:
Bull → Neutral → Bull → Neutral
→ full exit → re-entry → full exit
→ turnover + tax + slippage erodes alpha
### Target design (v0.2)
Regime-aware risk scaling instead of binary kill switch:
Bull:    100% exposure, normal sizing
Neutral: 30-50% exposure, tighter stops
Bear:    0-20%, no new entries, hold winners
Crisis:  0%, flat only
Requires: sizing infrastructure in paper_broker + position scaling logic.

### Research question for backtest
Measure regime flip frequency in 2021-2026 data:
- How often does regime transition Bull↔Neutral within 20 trading days?
- What is the round-trip cost (tax + fees) of each false transition?
- Does the current threshold create excessive turnover?

## Addendum 6 — Design decisions locked (2026-05-22)

### T+1 fill design: no change

Current cron: `daily_run --as-of yesterday`
- Signal date = yesterday's close
- Fill date = today's open (adj_open)
- Features used = yesterday's computed features (compute_features not in cron)

Decision: maintain as-is. Adding compute_features to cron (to use today's close
for signals) would push fill to T+2 open, adding one extra day of slippage risk
with no clear benefit for a trend-following system.
