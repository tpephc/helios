## 1. R8 MA5 Momentum — Phase 0 Feasibility (CLOSED)

New strategy family proposed: enter on a large bullish candle
(`daily_return >= +5% AND close > open`), manage around MA5. Phase 0 asked one
question only: is the entry population large, tradable, and distinct enough to
justify building an R8 lifecycle replay engine. It does NOT evaluate performance.

**Verdict: gate 5/5 PASS, but PASS authorises a lifecycle-replay SPEC ONLY** —
not a production rule, not a clean orthogonality claim. Two criteria pass on
threshold placement, not strength of evidence.

### Key findings

- Population: 8372 signals, 2021-06..2026-05, CA-excluded, regime[T-1]-tagged,
  99.94% inside dynamic_top200.
- Tradability (good news): T+1-open limit-lock is NOT a material risk (0.95%
  open >= +9.5%; next_open_ret median +0.48%). But ~29% of signal days closed
  near limit-up and open ~flat next day -> likely exhausted moves. Tradable !=
  good entry.
- **Selection-level redundancy (core finding):** de-circularised T-1 RS60
  top-tertile enrichment = **1.63** (vs base 0.33; tertile ceiling ~3.0).
  Circularity ruled out via T-1 lag. R8 lives in already-high-RS names.
  Screener-profile overlap (find_bullish_setups.py, [ASSUMED] thresholds):
  MOMENTUM 2.98 (partly constructive), COMPRESSION 0.16, RECLAIM 1.17.
  Pullback proxy (dist_above_ma20_atr<0) 0.31. => R8 selects the
  "high-RS + volume-breakout" universe (screener MOMENTUM branch); any
  independent edge can only come from ENTRY TIMING, not selection.
- Sampling caveats: `clean_tradable_events`=5621 is a ROW count, NOT independent
  n — 23.4% of events fall on days with >=20 simultaneous signals
  (event_days=1115, max 77/day). Population non-stationary (2024-2026
  back-loaded) and ELECTRONICS-concentrated: ~78% of signals are in the
  electronics complex (industry_code 24 semis 27% + 28 components 18% + 26/25/
  27/31/29/30). Same-day clustering and industry concentration are the same
  dependence; effective n is even lower.

### MANDATORY for the Phase 1 lifecycle SPEC (not optional)

(D2 confirmed R8 most resembles the screener MOMENTUM profile, so beating a plain
RS-momentum entry — not just RS hold — is required). R8 must beat "simply holding

## 2. Intraday Monitor Healthcheck (DEPLOYED)

Context: `intraday_monitor.py` runs on cron (`7,22,37,52 9-13 * * 1-5`). When it
dies fatally it writes NO DB row and sends NO alert — it can be silently down.
Confirmed: 2026-05-28 and 2026-05-29 at 09:05 both died with DuckDB lock
conflicts; `system_alert_sent` was 0.

New: `scripts/intraday_healthcheck.py` v0.1.0 — post-close, read-only watchdog.
Reconciles expected (20) vs actual DB runs AND scans the log for fatals/skips
(DB and log are independent views: a fatal leaves no DB row, so log is the only
fatal evidence). Alerts via the existing communication.telegram stack only on
fatal or coverage <80%; skips are reported but do not alert. `--dry-run` supported.

Verified end-to-end this session: coverage detection (today 5/20 mid-session ->
LOW COVERAGE), fatal detection (2026-05-28 caught despite 95% coverage), skip
non-alerting (2026-05-27 two skips -> HEALTHY), timezone day-attribution, and a
real Telegram send. Deployed:

```
0 14 * * 1-5  cd /home/tradeagent/projects/helios && \
  /home/tradeagent/.local/bin/uv run python scripts/intraday_healthcheck.py \
  >> logs/intraday_healthcheck.log 2>&1
```

Known residual gap (-> P2-OBS): a SINGLE missed run is 19/20 = 95% and passes
HEALTHY; single silent run-gaps with no fatal log line are undetectable by
coverage alone. Unverified assumption: whether the two post-close fires
(13:37/13:52) write DB rows — if they don't, use `--expected-runs 18`. Confirm by
inspecting a full trading day's run count.

## 4. Engineering Notes / Lessons

- Two bugs were only caught at real execution, not by `ast.parse`:
  (1) argparse help string `+10%` crashed `--help` (ValueError: unsupported
  format character) — fixed by escaping to `%%`;
  (2) `WHERE col = DATE ?` is invalid DuckDB — fixed to `CAST(? AS DATE)`,
  reproduced and verified against an in-memory DuckDB.
  Going forward: DB-query paths are checked against a real DuckDB before handoff,
  not by syntax parse alone.
- `stock_info` table is EMPTY; sector mapping uses `company_metadata.industry_code`
  (decoded from representative constituents, not an external code table).
- The R8 DQ diagnostic's first version had a join blow-up (cartesian on stock_id);
  classification figures here are from the corrected correlated-subquery version.
